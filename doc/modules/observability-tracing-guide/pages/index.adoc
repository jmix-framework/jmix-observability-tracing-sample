== What We are Going to Build

This guide focuses on enhancing the Petclinic Backend and Portal applications from the centralized logging guide with comprehensive distributed tracing capabilities.

Building upon the existing OpenTelemetry infrastructure, we will demonstrate how to track requests as they flow from the Portal frontend through the Backend to the database, providing complete visibility into distributed request execution.

The final application includes:

* *Automatic Instrumentation*: Zero-code tracing for HTTP requests, REST DataStore calls, and database queries that works immediately after configuration
* *Custom Business Tracing*: Manual spans for complex operations like owner registration, enriched with meaningful business context
* *Grafana Tempo Integration*: Complete trace visualization and analysis alongside existing logs in a unified observability interface
* *Cross-Service Correlation*: Track individual requests from Portal frontend through Backend to database with precise timing and error information

[[introduction-distributed-tracing]]
== Introduction to Distributed Tracing

Before diving into the technical setup, let's look at what distributed tracing is and why it becomes essential when working with multiple applications.

In the previous xref:observability-logging-guide:index.adoc[Centralized Logging Guide], we established the foundation for observability by bringing logs from multiple services into a single interface. Centralized logging was our first step toward understanding distributed systems - instead of searching through separate log files on different servers, we could view all logs in Grafana and even correlate them temporally to understand what was happening across services at a specific moment in time.

However, as systems grow and handle more concurrent requests, centralized logging alone reaches its limits. While we can see logs from different services in one place and correlate them by timestamp, this temporal correlation becomes increasingly difficult with higher load. When dozens or hundreds of requests are processed simultaneously, determining which log entries belong to the same user request becomes nearly impossible. Furthermore, centralized logging lacks causal correlation - there's no automatic way to understand the cause-and-effect relationships between events across services.

Distributed tracing addresses these limitations by adding a crucial capability: the ability to track a single request as it travels through multiple services, creating a complete picture of how different parts of your system interact to fulfill that request. While centralized logging gives us visibility into what's happening across services, distributed tracing adds the context of *why* and *how* these events are related.

Consider what happens when a pet owner logs into the Petclinic Portal and views their list of pets. This seemingly simple action actually involves multiple steps across different applications:

1. The Portal receives the user's request to view pets
2. Portal makes a REST API call to the Backend using the REST DataStore
3. Backend processes the request and queries the database
4. Database returns the pet data
5. Backend serializes the response back to Portal
6. Portal renders the pet list for the user

With traditional logging, each application would record its own activities independently. You might see a log entry in the Portal about loading pets, and separately, a log entry in the Backend about processing a pet query. However, there's no automatic way to connect these individual log entries into a single, cohesive story of what happened during that specific user request.

Distributed tracing solves this by creating a *trace* - a collection of related *spans* that represent the work done by each service for a single request. Each span contains timing information, operation details, and a unique identifier that links it to other spans in the same trace.

Think of it this way: logs are like individual photographs that capture moments in time across different locations, while traces are like a video that shows the complete journey of a request through your system, revealing the connections between those moments.

By building distributed tracing on top of our centralized logging foundation, we gain several key benefits:

* **Request Flow Visibility**: See exactly how a request moves through your system and where time is spent
* **Performance Analysis**: Identify bottlenecks by examining which operations take the longest
* **Error Correlation**: When something goes wrong, trace the exact path that led to the error
* **Service Dependencies**: Understand how your services interact and depend on each other
* **Causal Relationships**: Unlike temporal correlation in centralized logging, traces reveal the actual cause-and-effect chain between events

In distributed systems, this enhanced visibility becomes critical for understanding system behavior, diagnosing issues, and optimizing performance across service boundaries. Distributed tracing complements centralized logging by adding the missing piece: automatic correlation of related events across services, even under high load with many parallel requests.

[[spring-boot-actuator-and-micrometer]]
== Spring Boot Actuator and Micrometer Tracing

Before configuring the specific tracing dependencies, it's important to understand the foundation that Jmix and Spring Boot already provide for observability.

As described in the xref:observability-logging-guide:index.adoc#spring-boot-actuator[Centralized Logging Guide], Spring Boot Actuator serves as the main way to expose operational data from applications. While Actuator itself is not included by default in Jmix applications, the underlying Micrometer dependencies are already present through Spring Boot.

With Spring Boot 3, Micrometer has evolved beyond just metrics collection to provide a comprehensive observability facade that includes:

* **Micrometer Observation API**: A unified API for instrumenting code once and getting both metrics and traces
* **Micrometer Tracing**: A vendor-neutral tracing facade that works with different implementations (OpenTelemetry, Brave/Zipkin, AWS X-Ray)

This means Jmix applications already have the foundation for distributed tracing built in through these Micrometer dependencies. When we add `spring-boot-starter-actuator` and `micrometer-tracing-bridge-otel` in the next sections, we're:

1. Enabling Actuator to expose the observability features
2. Telling Micrometer to use OpenTelemetry as its tracing implementation

The bridge translates Micrometer's observations into OpenTelemetry spans, providing automatic instrumentation for HTTP requests, database calls, and other operations without requiring any code changes.

[NOTE]
====
Because Jmix includes Micrometer through Spring Boot, the foundation for distributed tracing is already present. This makes enabling tracing primarily a matter of adding Actuator and configuring which tracing backend to use.
====

[[docker-environment-configuration]]
=== Configuring the Docker Environment

When running the applications in Docker containers, the tracing endpoints need to be configured to point to the internal Docker network addresses. The `docker-compose.yaml` file includes environment variables that override the local development settings:

.docker-compose.yaml - Environment variables for tracing
[source,yaml,indent=0]
----
environment:
  # ... other environment variables ...
  # Logging export
  MANAGEMENT_OTLP_LOGGING_ENDPOINT: http://otel-collector:4318/v1/logs
  # Tracing export
  MANAGEMENT_OTLP_TRACING_ENDPOINT: http://otel-collector:4318/v1/traces
----

These environment variables override the `application.properties` settings when running in Docker, ensuring that the applications can reach the OpenTelemetry Collector using the internal Docker network hostname (`otel-collector`) instead of `localhost`.

[[verifying-setup]]
=== Verifying the Tracing Setup

With all components configured, let's verify that our distributed tracing setup works correctly.

. Start the complete infrastructure including the new Tempo service:
+
[source,bash]
----
docker-compose -f docker/docker-compose.yaml up -d
----

. Start both the Petclinic Backend and Portal applications (either locally or via Docker)

. Open Grafana at http://localhost:3000 (username: `admin`, password: `admin`)

. Navigate to **Configuration > Data sources** and verify that both Loki and Tempo appear as configured data sources

. In Grafana, go to **Explore** and select **Tempo** from the data source dropdown

If the setup is working correctly, you should see Tempo available as a data source. The applications will begin sending traces to the Collector, which forwards them to Tempo for storage and querying.

[NOTE]
====
Traces may take 30-60 seconds to appear in Tempo after application startup as the OpenTelemetry SDK initializes and begins exporting data.
====
