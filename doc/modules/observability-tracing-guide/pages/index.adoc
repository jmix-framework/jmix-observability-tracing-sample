[[what-we-are-going-to-build]]
== What We are Going to Build

This guide focuses on enhancing the Petclinic Backend and Portal applications from the centralized logging guide with comprehensive distributed tracing capabilities.

Building upon the existing OpenTelemetry infrastructure, we will demonstrate how to track requests as they flow from the Portal frontend through the Backend to the database, providing complete visibility into distributed request execution.

The final application includes:

* *Automatic Instrumentation*: Zero-code tracing for HTTP requests, REST DataStore calls, and database queries that works immediately after configuration
* *Custom Business Tracing*: Manual spans for complex operations like owner registration, enriched with meaningful business context
* *Grafana Tempo Integration*: Complete trace visualization and analysis alongside existing logs in a unified observability interface
* *Cross-Service Correlation*: Track individual requests from Portal frontend through Backend to database with precise timing and error information

[[introduction-distributed-tracing]]
== Introduction to Distributed Tracing

Before diving into the technical setup, let's look at what distributed tracing is and why it becomes essential when working with multiple applications.

Distributed tracing is the ability to track a single request as it travels through multiple services, creating a complete picture of how different parts of your system interact to fulfill that request.

Consider what happens when a pet owner logs into the Petclinic Portal and views their list of pets. This seemingly simple action actually involves multiple steps across different applications:

1. The Portal receives the user's request to view pets
2. Portal makes a REST API call to the Backend using the REST DataStore
3. Backend processes the request and queries the database
4. Database returns the pet data
5. Backend serializes the response back to Portal
6. Portal renders the pet list for the user

With traditional logging, each application would record its own activities independently. You might see a log entry in the Portal about loading pets, and separately, a log entry in the Backend about processing a pet query. However, there's no automatic way to connect these individual log entries into a single, cohesive story of what happened during that specific user request.

Distributed tracing solves this by creating a *trace* - a collection of related *spans* that represent the work done by each service for a single request. Each span contains timing information, operation details, and a unique identifier that links it to other spans in the same trace.

Think of logs as individual photographs that capture moments in time, while traces are like a video that shows the complete journey of a request through your system.

This approach provides several key benefits:

* **Request Flow Visibility**: See exactly how a request moves through your system and where time is spent
* **Performance Analysis**: Identify bottlenecks by examining which operations take the longest
* **Error Correlation**: When something goes wrong, trace the exact path that led to the error
* **Service Dependencies**: Understand how your services interact and depend on each other

In distributed systems, this visibility becomes critical for understanding system behavior, diagnosing issues, and optimizing performance across service boundaries.

[[verifying-setup]]
=== Verifying the Tracing Setup

With all components configured, let's verify that our distributed tracing setup works correctly.

. Start the complete infrastructure including the new Tempo service:
+
[source,bash]
----
docker-compose -f docker/docker-compose.yaml up -d
----

. Start both the Petclinic Backend and Portal applications

. Open Grafana at http://localhost:3000 (username: `admin`, password: `admin`)

. Navigate to **Configuration > Data sources** and verify that both Loki and Tempo appear as configured data sources

. In Grafana, go to **Explore** and select **Tempo** from the data source dropdown

If the setup is working correctly, you should see Tempo available as a data source. The applications will begin sending traces to the Collector, which forwards them to Tempo for storage and querying.

[NOTE]
====
Traces may take 30-60 seconds to appear in Tempo after application startup as the OpenTelemetry SDK initializes and begins exporting data.
====
